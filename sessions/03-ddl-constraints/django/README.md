# Session 03 in Django: constraints in the database

The recipe schema from the session 03 tutorial written as Django models. Every `CHECK`, `UNIQUE` and foreign key is created in PostgreSQL by the migration, and the API turns each violation into a 409 or 422 that names the constraint.

| File | What it shows |
|------|---------------|
| `demo/models.py` | `Meta.constraints` with `CheckConstraint(condition=...)` and `UniqueConstraint`, each with a name we chose. `on_delete=DB_CASCADE` and `DO_NOTHING` on the foreign keys. |
| `demo/migrations/0001_initial.py` | Generated by `makemigrations`. Run `uv run python manage.py sqlmigrate demo 0001` to read the DDL and compare it with the tutorial's `001_create_tables.sql`. |
| `demo/errors.py` | Reads the SQLSTATE and constraint name from the psycopg error that Django wraps: unique violation (23505) becomes 409, check, foreign key and not-null violations become 422. |
| `demo/views.py` | `POST /authors`, `POST /ingredients`, `POST /recipes` (with its ingredient lines in one transaction). No validation in Python, so the database is the one saying no. |
| `demo/management/commands/try_invalid.py` | The tutorial's invalid inserts plus a few more, deleting an author who has recipes (refused) and deleting a recipe (its lines are deleted by the database). |

## Where the rules live

| Tutorial DDL | Django | Enforced by |
|--------------|--------|-------------|
| `integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | `AutoField(primary_key=True, db_column=...)` | Database, but Django creates `GENERATED BY DEFAULT AS IDENTITY`, so an explicit id in an `INSERT` is accepted. |
| `NOT NULL`, `DEFAULT now()` | every field without `null=True`; `db_default=Now()` | Database. Use `db_default`, not `default`, when the default must exist in the table. |
| `UNIQUE`, `UNIQUE (author_id, title)`, `CHECK (...)` | `UniqueConstraint`, `CheckConstraint` in `Meta.constraints` | Database. Django can also check them before saving with `full_clean()`, but that check runs before the insert and two requests can both pass it. |
| `ON DELETE CASCADE` on `recipe_ingredient.recipe_id` | `on_delete=models.DB_CASCADE` (new in Django 6.1) | Database. Django sends one `DELETE FROM recipe` and PostgreSQL removes the lines. |
| `ON DELETE RESTRICT` on `recipe.author_id` and `recipe_ingredient.ingredient_id` | `on_delete=models.DO_NOTHING` | Database, as `NO ACTION`. Django 6.1 has no `DB_RESTRICT`. |

About `RESTRICT`: Django's `models.RESTRICT` and `models.PROTECT` are emulated in Python. Before a delete, Django queries the related rows and raises `RestrictedError` or `ProtectedError`; nothing is added to the foreign key, and a `DELETE` from `psql` or another app is not checked by Django at all. They also cannot be combined with `DB_CASCADE` in the same chain of references: try changing `Recipe.author` to `models.RESTRICT` and `uv run python manage.py check` reports `fields.E323`. `DO_NOTHING` leaves the decision to the foreign key, which PostgreSQL enforces as `NO ACTION`. `NO ACTION` and `RESTRICT` both refuse the delete; the difference is when. Django creates every foreign key as `DEFERRABLE INITIALLY DEFERRED`, so inside a transaction the error appears at `COMMIT`, not at the `DELETE` statement. To get the exact tutorial behaviour you would replace the constraint with a hand-written `migrations.RunSQL`.

Django names foreign keys itself (`recipe_author_id_9abf18d1_fk_author_author_id`); only `CHECK` and `UNIQUE` constraints take the name you give them.

## Run it

From the root of the repository:

```bash
docker compose up -d
./scripts/create-db.sh s03_django
```

Then, in this folder:

```bash
cp .env.example .env
uv sync
uv run python manage.py migrate
uv run python manage.py sqlmigrate demo 0001
uv run python manage.py runserver 8001
```

`uv sync` creates `.venv/` with the Python version and the exact package versions in `uv.lock`. The dependencies are declared in `pyproject.toml`.

On a new database the first author, ingredient and recipe get id 1:

```bash
curl -X POST localhost:8001/authors -H 'content-type: application/json' -d '{"name": "Rui", "email": "rui@example.com"}'
curl -X POST localhost:8001/authors -H 'content-type: application/json' -d '{"name": "Rui again", "email": "rui@example.com"}'   # 409 author_email_unique
curl -X POST localhost:8001/ingredients -H 'content-type: application/json' -d '{"name": "Egg", "kcal_per_100g": 155}'
curl -X POST localhost:8001/ingredients -H 'content-type: application/json' -d '{"name": "Sugar", "kcal_per_100g": -1}'   # 422 ingredient_kcal_not_negative
curl -X POST localhost:8001/recipes -H 'content-type: application/json' \
  -d '{"author_id": 1, "title": "Omelette", "servings": 1, "ingredients": [{"ingredient_id": 1, "grams": 120}]}'
curl -X POST localhost:8001/recipes -H 'content-type: application/json' -d '{"author_id": 1, "title": "Omelette", "servings": 1}'  # 409 recipe_author_title_unique
curl -X POST localhost:8001/recipes -H 'content-type: application/json' -d '{"author_id": 999, "title": "Soup", "servings": 4}'    # 422 foreign key
curl -X POST localhost:8001/recipes -H 'content-type: application/json' -d '{"author_id": 1, "title": "Feast", "servings": 80}'   # 422 recipe_servings_1_to_50
```

Then run every invalid case at once:

```bash
uv run python manage.py try_invalid
```

## Things to try

- Run the tutorial's inserts in `psql` (`docker compose exec postgres psql -U postgres -d s03_django` from the repository root). They fail with the same constraint names, because the rules are in the database and not in Django.
- `DELETE FROM author WHERE email = 'ana@example.com';` in `psql` fails. Then `BEGIN; DELETE FROM author WHERE email = 'ana@example.com';` succeeds until you type `COMMIT;`: that is the deferred foreign key.
- `INSERT INTO author (author_id, name, email) VALUES (500, 'Eva', 'eva@example.com');` is accepted with `BY DEFAULT`. In the tutorial's `ALWAYS` version it is refused.
- In `uv run python manage.py shell`, build `Ingredient(name="Salt", kcal_per_100g=-5)` and call `.full_clean()`. Django raises `ValidationError` without inserting anything. Wrap the call in `CaptureQueriesContext` (from `django.test.utils`) to see how: it runs a `SELECT` for an existing `Salt` and another that asks PostgreSQL to evaluate the `CHECK` expression on the values.
- Change `Recipe.author` to `on_delete=models.RESTRICT`, run `uv run python manage.py check` and read error `fields.E323`.
