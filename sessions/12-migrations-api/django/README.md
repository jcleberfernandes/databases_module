# Session 12 in Django: migrations on an existing database and a locked charge endpoint

The session 12 tutorial with Django migrations instead of Alembic: a baseline for a table that already exists in Pagila, a `balance` column, the three-step `tier` migration with a working downgrade, and `POST /customers/{id}/charge` with a row lock and `409` when the balance is too low.

| File | What it shows |
|------|---------------|
| `demo/models.py` | `Customer` mapped to the Pagila table and managed by Django from now on. Only the mapped columns are touched. |
| `demo/migrations/0001_baseline.py` | Written by hand: `SeparateDatabaseAndState` records the existing table in Django's state and runs no SQL. |
| `demo/migrations/0002_customer_balance.py` | `balance numeric(10,2) NOT NULL DEFAULT 0`, generated by `makemigrations` from `db_default=0`. |
| `demo/migrations/0003` to `0005` | The tutorial's three steps: add `tier` as nullable, backfill it from `active` (`RunPython`), set `NOT NULL`. |
| `demo/views.py` | `GET /customers/{id}`, `POST /customers/{id}/charge` (`transaction.atomic()` and `select_for_update()`), `POST /customers/{id}/top-up`. |
| `config/settings.py` | `conn_max_age`: how long Django keeps a connection open between requests. |

## Baseline: why not `--fake-initial` or `managed = False`

Alembic marks an existing database with `alembic stamp`. Django has three options:

- `managed = False` (sessions 11, 13...): Django never changes the table, so it could not add `balance` or `tier`.
- A normal `CreateModel` migration applied with `migrate --fake-initial`: Django skips it because the table exists. It works, but `migrate demo zero` would later run `DROP TABLE customer CASCADE` on real data.
- `SeparateDatabaseAndState` with no database operations (used here): the migration updates Django's state only. Applying or reversing it runs no SQL, and every migration after it is a normal one.

## Run it

From the root of the repository:

```bash
docker compose up -d
./scripts/create-db.sh s12_django --pagila
```

Then, in this folder:

```bash
cp .env.example .env
uv sync
uv run python manage.py showmigrations demo
uv run python manage.py sqlmigrate demo 0002      # read the SQL before applying it
uv run python manage.py migrate
uv run python manage.py migrate demo 0002         # downgrade: undoes 0005, 0004 and 0003
uv run python manage.py migrate                   # and up again
uv run python manage.py runserver 8001
```

`uv sync` creates `.venv/` with the Python version and the exact package versions in `uv.lock`. The dependencies are declared in `pyproject.toml`.

```bash
curl localhost:8001/customers/1
curl -X POST localhost:8001/customers/1/charge -H 'content-type: application/json' -d '{"amount": 5}'      # 409, balance is 0
curl -X POST localhost:8001/customers/1/top-up -H 'content-type: application/json' -d '{"amount": "20.00"}'
curl -X POST localhost:8001/customers/1/charge -H 'content-type: application/json' -d '{"amount": 7.5}'    # 200, balance 12.50
curl -X POST localhost:8001/customers/1/charge -H 'content-type: application/json' -d '{"amount": -1}'     # 422
curl -X POST localhost:8001/customers/99999/charge -H 'content-type: application/json' -d '{"amount": 1}'  # 404
```

## Things to try

- Fire 20 charges of 1 at once at a balance of 12.50. Exactly 12 return `200` and the balance ends at `0.50`:

  ```bash
  seq 20 | xargs -P 20 -I{} curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8001/customers/1/charge \
      -H 'content-type: application/json' -d '{"amount": 1}' | sort | uniq -c
  ```

  Remove `.select_for_update()` from `charge`, top up another customer to 12.50 and run it again: more than 12 charges (often all 20) return `200`, yet the balance does not go any lower. Several requests read the same balance before any of them wrote, so their charges overwrote each other: a lost update.
- After `migrate demo 0002`, run `\d customer` in `psql` (`docker compose exec postgres psql -U postgres s12_django` from the repository root): `tier` is gone and `balance` is still there.
- On PostgreSQL each Django migration runs in its own transaction. Make `fill_tier` raise an exception, go back to 0002 and run `migrate`: 0003 is applied (the nullable column exists), 0004 is rolled back and not recorded, and `migrate` continues from there once you fix it.
- Go back to 0002, move 0003 to 0005 out of the folder and declare `tier = models.TextField()` directly. `makemigrations` asks for a one-off default for the existing rows: one value for every row, where the backfill computes it per row from `active`.
- Set `ATOMIC_REQUESTS = True` on the database in `settings.py` to wrap every request in a transaction. It is simpler, but each request then holds its transaction (and any locks) until the response is built.
