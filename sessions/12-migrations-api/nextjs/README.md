# Session 12 in Next.js with Prisma: migrations, transactions and API

Baselines Prisma Migrate on an existing Pagila database, adds `customer.balance` and the three-step `customer.tier` migration from the session 12 tutorial, reverts and reapplies it, and exposes the charge endpoint with a row lock.

| File | What it shows |
|------|---------------|
| `prisma/schema.prisma` | The whole Pagila schema from `npx prisma db pull`, plus `balance` and `tier` on `customer`. |
| `prisma/migrations/0_init/` | The baseline: SQL for the existing tables, marked as applied without running it. |
| `prisma/migrations/*_add_customer_balance/` | `balance numeric(10,2) NOT NULL DEFAULT 0`, generated by `prisma migrate dev`. |
| `prisma/migrations/*_add_customer_tier/` | Created with `--create-only` and edited by hand into add nullable, backfill from `active`, set `NOT NULL`. |
| `prisma/migrations/*/down.sql` | Hand-written reverse of each migration. Prisma Migrate has no `downgrade`. |
| `scripts/migrate-down.ts` | `npm run db:down`: runs the last migration's `down.sql` and marks it as rolled back, in one transaction. |
| `src/app/api/customers/[id]/charge/route.ts` | Interactive `$transaction` with `SELECT ... FOR UPDATE` through `$queryRaw`; 404, 409 and 422. |
| `src/app/api/customers/[id]/top-up/route.ts` | `balance: { increment }`, an atomic `UPDATE`, so the charge can be tried. |
| `src/lib/amount.ts` | Request validation: `amount` greater than 0 with at most 2 decimal places. |

| Alembic / SQLAlchemy | Prisma |
|----------------------|--------|
| `alembic revision --autogenerate` | `prisma migrate dev --create-only --name ...` |
| `alembic upgrade head` | `prisma migrate deploy` (or `prisma migrate dev` while developing) |
| `alembic downgrade -1` | not available: `down.sql` plus `npm run db:down` in this project |
| `alembic stamp` on an existing database | `prisma migrate resolve --applied 0_init` |
| `with session.begin():` | `prisma.$transaction(async (tx) => { ... })` |
| `select(...).with_for_update()` | ``tx.$queryRaw`SELECT ... FOR UPDATE` `` |

### Why the whole schema and not only `customer`

`prisma migrate dev` compares the database with the result of replaying every migration in a temporary shadow database. If the schema (and so `0_init`) only described `customer`, the other Pagila tables would look like drift and Prisma would ask to reset the database, deleting all the data. Baselining the full `db pull` output avoids that. The partitions of `payment`, the views, functions and triggers are not in the Prisma schema, and drift detection ignores them.

### How the baseline was made

```bash
npx prisma db pull
mkdir -p prisma/migrations/0_init
npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script -o prisma/migrations/0_init/migration.sql
npx prisma migrate resolve --applied 0_init
```

Then `balance` was added to the schema and `npx prisma migrate dev --name add_customer_balance` generated and applied the migration. For `tier`, `npx prisma migrate dev --create-only --name add_customer_tier` generated `ADD COLUMN "tier" TEXT NOT NULL` and warned that it cannot run on a table with 999 rows. The file was edited into the three steps and applied with `npx prisma migrate dev`.

## Run it

From the root of the repository, start the engines and create this project's database as a copy of Pagila:

```bash
docker compose up -d
./scripts/create-db.sh s12_nextjs --pagila
```

Then, in this folder:

```bash
cp .env.example .env
npm install
npx prisma migrate resolve --applied 0_init   # the tables already exist
npm run db:deploy                             # applies balance and tier
npm run db:status
npm run dev
```

Revert the last migration and apply it again, as in the tutorial:

```bash
npm run db:down      # Reverted ..._add_customer_tier
npm run db:status    # one migration not yet applied
npm run db:deploy
```

```bash
curl localhost:3000/api/customers/1
curl -X POST localhost:3000/api/customers/1/charge -H 'content-type: application/json' -d '{"amount": 10}'   # 409
curl -X POST localhost:3000/api/customers/1/top-up -H 'content-type: application/json' -d '{"amount": 50}'
curl -X POST localhost:3000/api/customers/1/charge -H 'content-type: application/json' -d '{"amount": 10.50}' # balance 39.5
curl -X POST localhost:3000/api/customers/1/charge -H 'content-type: application/json' -d '{"amount": -1}'    # 422
curl -X POST localhost:3000/api/customers/9999/charge -H 'content-type: application/json' -d '{"amount": 1}'  # 404
```

## Things to try

- Fire 10 charges of 5 at the same time against a balance of 39.50. Exactly 7 succeed and the balance ends at 4.50:

  ```bash
  seq 10 | xargs -P10 -I{} curl -s -o /dev/null -w "%{http_code}\n" -X POST localhost:3000/api/customers/1/charge \
      -H 'content-type: application/json' -d '{"amount": 5}' | sort | uniq -c
  ```

  Remove `FOR UPDATE` from the charge route and try again: some charges read the same balance and overwrite each other.
- Run `npm run db:down` twice. The second call reverts `add_customer_balance`. A third call stops because `0_init` has no `down.sql`: reverting the baseline would drop Pagila.
- Put the unedited one-line `ADD COLUMN "tier" TEXT NOT NULL` back in the migration, run `npm run db:down` and `npm run db:deploy`, and read the error. Prisma records the migration as failed; restore the three-step file, run `npx prisma migrate resolve --rolled-back <name>` and deploy again.
- Change one character in an applied migration and run `npx prisma migrate dev` (without `--create-only`): it reports that the migration was modified after it was applied and offers to reset the database. Answer no, and undo the change.
- In `psql`, `SELECT migration_name, finished_at, rolled_back_at FROM _prisma_migrations;` shows the history Prisma keeps, including reverted runs.
