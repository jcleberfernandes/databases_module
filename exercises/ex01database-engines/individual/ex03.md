# 100.000 registros e dois usuários escrevendo ao mesmo tempo

## 100.000 registros

### PostgreSQL

O PostgreSQL consegue guardar 100.000 mensagens na tabela `hello` sem um
problema imediato. Porém, o programa abre uma nova conexão toda vez que
precisa falar com o banco, nas linhas 18–20 de
[`fastapi/app/clients.py`](./fastapi/app/clients.py).

Com muitas pessoas usando o programa ao mesmo tempo, abrir muitas conexões
pode deixar a aplicação lenta. Além disso, a leitura busca somente as cinco
mensagens mais recentes, nas linhas 79–81 de
[`fastapi/app/main.py`](./fastapi/app/main.py). Não é possível ver todas as
100.000 mensagens de uma vez.

**Como melhorar:** mostrar as mensagens em páginas, por exemplo, 20 ou 50 por
vez, e reaproveitar as conexões com o banco.

### MongoDB

O MongoDB também consegue guardar 100.000 documentos. Atualmente, o programa
busca somente os cinco últimos documentos, nas linhas 83–85 de
[`fastapi/app/main.py`](./fastapi/app/main.py).

Se no futuro for necessário procurar mensagens por texto ou por data, a busca
pode ficar mais lenta, pois o programa ainda não criou uma regra especial para
essas buscas.

**Como melhorar:** continuar mostrando poucos documentos por vez e criar
formas de busca para os campos que forem usados com frequência.

### Redis

O Redis não guarda todas as mensagens neste exemplo. A chave `hello:last`,
usada nas linhas 66–67 de [`fastapi/app/main.py`](./fastapi/app/main.py),
guarda somente a última mensagem. A chave `hello:count` guarda apenas o número
de mensagens.

Se o programa passasse a guardar as 100.000 mensagens no Redis, ele precisaria
de muita memória. Por isso, o Redis é mais indicado aqui para guardar a última
mensagem ou um contador, e não todo o histórico.

**Como melhorar:** manter as mensagens no PostgreSQL e usar o Redis somente
para informações rápidas que possam ser criadas novamente.

## Dois usuários escrevendo ao mesmo tempo

Se duas pessoas enviarem mensagens quase no mesmo momento, o PostgreSQL deve
guardar as duas linhas. O campo `id` é criado pelo próprio banco, então os
dois registros recebem números diferentes.

O MongoDB também deve guardar os dois documentos, cada um com seu próprio
identificador.

No Redis, o contador da linha 67 de
[`fastapi/app/main.py`](./fastapi/app/main.py) deve aumentar duas vezes. Porém,
as duas mensagens usam o mesmo nome `hello:last`, na linha 66. Assim, uma
mensagem pode substituir a outra, e ficará visível somente a última mensagem
salva.

Também pode acontecer de o PostgreSQL salvar uma mensagem e o MongoDB
apresentar um erro logo depois. Nesse caso, os bancos ficam com informações
diferentes, porque cada parte é salva separadamente nas linhas 54–67 de
[`fastapi/app/main.py`](./fastapi/app/main.py).

**Como melhorar:** escolher o PostgreSQL como banco principal, dar um
identificador para cada mensagem e usar o Redis somente para dados que não
sejam o único lugar onde a informação está guardada.
